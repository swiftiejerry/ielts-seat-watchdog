# IDP 考位监控（独立模块）

这是与 NEEA 控制面**完全独立**的第二套数据源。两者刻意不混在同一个容器里：

| | NEEA (ielts.neea.cn) | IDP (sign.idpielts.cn) |
|---|---|---|
| 防护 | 瑞数动态 WAF，纯 HTTP 一律 412 | 无，裸 urllib 直接 200 |
| 登录 | 必须，且要过验证码 | 免登录，免验证码 |
| 请求量 | 城市×日期逐个查 | 一次 POST 拿全量 |
| 响应 | 明文 JSON | SM4-CBC 加密 |
| 部署 | Chrome + 油猴 + OCR 重登 | 纯 Python 常驻容器 |

## 为什么能高频

IDP 没有瑞数那种请求级授权层。实测：

```
1 秒间隔   × 60 次 → 60/60 成功，平均 0.43s
0.25 秒间隔 × 80 次 → 80/80 成功，平均 0.43s（4 req/s 持续 20 秒）
2 秒间隔   × 150 次 → 150/150 成功，零失败（持续 5 分钟）
```

且返回的是实时数据而非缓存快照——5 分钟全量比对抓到过真实变化
（某考点报名人数 15→16）。响应头也是 `cache-control: no-store`。

不过接口本身支持 4 req/s，不等于该跑那么快。IDP 是先到先得即时扣位，
没有 NEEA 那种 10:00/20:00 定时放位，30 秒一轮已经足够。

## 判定「有位」的两个条件

```python
官方未标记满  且  数值上还有余量
```

两个条件缺一不可，理由都是实测出来的：

- 只看 `fullyBooked` 会误报。官方标记会滞后：实测某场次从 34/35 涨到
  35/35 时 `fullyBooked` 仍是 `'0'`，报出去用户点进去发现是满的。
- 只看余量也会误报。179 条 `fullyBooked='1'` 的记录里有 97 条
  `signUpCount < participantsCount`（超售/锁位），余量看着是正的，
  但网站不放人。

## 三种日期模式

| 模式 | 行为 |
|---|---|
| `rolling` | 自动盯未来 N 天，窗口跟着今天滚，永不过期（推荐） |
| `all` | 盯该考点全部场期 |
| `list` | 只盯指定日期（这个模式才有"过期"概念，会每天 00:00/09:00 作废） |

`rolling` 之所以是默认：日期不写死在配置里，结构上不可能过期，
不需要手动重选，也不会出现"监控范围归零但没人发现"。

## 运行

```bash
docker compose up -d ielts-idp
```

面板：`http://127.0.0.1:9897`——考点、日期、场次、间隔、夜间降频、
推送 token 都能点，保存即热加载，不用重启容器。

配置接口：

```bash
curl http://127.0.0.1:9897/api/schedule   # 该考点真实考期（别用日历推算）
curl http://127.0.0.1:9897/api/config     # 读配置（token 已隐去）
curl http://127.0.0.1:9897/api/status     # 运行状态
```

## 已知风险

**SM4 密钥会轮换。** 密钥 `065574e7...` 和 IV 硬编码在前端 bundle 里，
IDP 随时可以换。换了这个脚本立刻失效——轮询会开始报错，
`/api/status` 的 `last_error` 能看到。这是长期维护的主要隐患，
NEEA 那边不存在这个问题（接口稳定）。

换密钥后要改 `idp_monitor.py` 顶部的 `SM4_KEY` / `SM4_IV`，
新值去 `https://www.idpielts.cn/assets/js/index-*.js` 里搜
`065574e7` 或 `sm4.encrypt` 附近找。

## 与公开仓库的边界

IDP 大陆只有机考，没有纸笔、没有 UKVI。要考纸笔的话这条路走不通。
